# End-to-End 테스트 결과

- 테스트 일자: 2026-10-13
- 대상 커밋: `5f98bc6` (Cache int8-quantized DiT weights on disk for fast loading)
- 방식: 실제 모델(Qwen-Image 2.1)로 백엔드 서버를 띄우고, 브라우저(프론트)와 `curl`/스크립트로 직접 요청

### 측정 시 주의
- 이 머신은 시험 내내 메모리가 빠듯했습니다. 시간은 절대값보다 **같은 조건끼리의 상대 비교**로 읽어야 합니다.
- 이 테스트 전에 한 일부 측정(768 bf16 26~40초/스텝, 첫 int8 시도 30초/스텝)은 **종료됐지만 `UN` 상태로 남은 프로세스가 스왑을 점유**한 상태에서 측정돼 오염됐습니다. 이 문서의 수치는 프로세스를 정리하고 서버를 새로 띄운 뒤 다시 측정한 값입니다.
- 서버 로그에서 시간을 뽑을 때 `이미지 생성 완료 (N초)`는 **생성(스텝) 구간만**이고 모델 로딩 시간은 포함하지 않습니다.

## 3. 항목별 상세

### 3.1 UI 기본 흐름 (브라우저)

| 확인 | 결과 |
|---|---|
| 기본값 표시 | Height 768, Width 768, Steps 20, Seed 42, Precision `bf16` 로 표시됨 |
| 빈 프롬프트로 생성 | 빨간색 "prompt를 입력하세요." 표시, 요청 안 감 |
| int8 / 512×512 / 8스텝 생성 | `queued`(0/8) → 진행률 증가 → `completed`(8/8, 100%), 이미지 표시. 버튼은 생성 중 "생성 중..."으로 비활성화 후 복구 |
| 요청의 precision 저장 | DB에 `int8`, 512, 512, 8로 기록됨 |
| bf16 / 512×512 / 8스텝 생성 | 정상 완료, 이미지 표시 |
| task_id 조회 (완료된 작업) | 상태·진행률·이미지 정상 표시 |
| task_id 조회 (없는 ID) | 빨간 "태스크 상태 요청 실패: 400" 표시 (문제 4 참고) |

시간(서버 로그):
- int8 첫 요청: 인코더 로딩 약 35초(21:04:16→21:04:51) → 캐시에서 DiT 로딩 → 생성 26.6초
- bf16 요청(같은 프롬프트): "프롬프트 임베딩 캐시 사용 (인코더 로딩 생략)" → 생성 34.4초
- 프론트가 호출한 API: `GET /api/v1/tasks/{id}` 폴링(1.5초 간격) 후 `GET /api/v1/tasks/{id}/result` 200

관찰:
- 상태가 `completed`로 바뀐 직후 결과 이미지를 받아오는 동안(약 1~5초) "아직 생성된 이미지 없음."이 잠깐 보입니다. 결과 요청은 정상이라 버그는 아니고, 로딩 표시가 없을 뿐입니다.

### 3.2 요청 묶음과 큐

**시나리오**: 프롬프트 4종 × 정밀도 2종(8개 요청, 512×512, 20스텝, 시드 7). 첫 요청(`text`/int8)을 먼저 보내고 2초 뒤에 나머지 7개를 보냄.

| 구간 | 로그 | 시간 |
|---|---|---|
| 배치 1 (요청 1개) | 인코더 로딩(프롬프트 1개) → int8 DiT 캐시 로딩 → 생성 | 인코더 약 29초, 생성 64.6초 |
| 배치 2 (요청 7개) | **인코더 1번 로딩(프롬프트 3개)** | 약 145초 (21:08:55→21:11:20) |
| ↳ bf16 그룹 | **DiT 1번 로딩**, 이미지 4장 | 생성 73.4 / 123.4 / 133.5 / 134.2초 |
| ↳ int8 그룹 | **DiT 1번 로딩**, 이미지 3장 | 생성 65.7 / 65.2 / 64.7초 |

완료 순서(요청 시작 기준 경과 시간): `text-int8` 101초 → `text-bf16` 333초 → `face-bf16` 459초 → `glass-bf16` 591초 → `ko-bf16` 726초 → `face-int8` 798초 → `glass-int8` 861초 → `ko-int8` 927초. 8개 모두 `completed`.

확인된 동작:
- **동시에 `processing`인 작업은 최대 1개**였습니다 (3초 간격으로 DB 폴링).
- 배치 1이 끝났을 때 `text-bf16`은 프롬프트가 캐시돼 있었지만 정밀도가 달라 **DiT 재로딩 없이 이어서 처리하는 대상에서 제외**되고 다음 배치로 넘어갔습니다 (같은 정밀도만 이어서 처리하는 규칙과 일치).
- 같은 프롬프트는 정밀도가 달라도 임베딩 캐시를 재사용해 인코더 로딩이 생략됩니다 (3.1의 bf16 요청에서도 확인).

관찰:
- 같은 로딩된 DiT로 연속 생성할 때 bf16은 73초에서 134초까지 점점 느려졌고, int8은 약 65초로 일정했습니다. 메모리 압박이 누적된 영향으로 보이지만 원인을 추가로 분리하지는 않았습니다.
- 인코더가 프롬프트 3개를 처리하는 데 145초가 걸렸습니다(프롬프트 1개일 때 약 27~35초). 스왑 압박이 큰 시점이었습니다.

사전 시험(같은 서버, 512×512, 20스텝): int8 요청 1개 → 이어서 bf16 1, int8 1, bf16 1개를 보냈을 때 int8 DiT 1번 + 캐시된 int8 요청 이어서 처리 + bf16 DiT 1번으로 총 4개가 완료됨 (생성 64.8 / 64.5 / 69.1 / 98.4초).

### 3.3 int8 디스크 캐시

| 시나리오 | 결과 |
|---|---|
| 캐시 삭제 후 첫 int8 요청 | 인코더 약 27초 → DiT 로딩+양자화 약 13초(21:23:44→21:23:57) → 캐시 저장 약 1초 → 생성. 캐시 파일 7,118,160,304 bytes(약 6.6GiB) 생성 |
| 서버 재시작 후 int8 요청 | 로그 "int8 가중치 캐시에서 DiT 로딩". DiT 로딩 약 5초 (완료 시각에서 생성 시간 14.0초를 뺀 값) |
| 서버 실행 중 캐시를 **잘린 파일**(앞 100MB만)로 교체 | 경고 `Error while deserializing header: incomplete metadata, file not fully covered` → 자동 재양자화 → 캐시 재저장, 요청 `completed` |
| 서버 실행 중 캐시를 **쓰레기 데이터**(5KB)로 교체 | 경고 `Error while deserializing header: header too large` → 자동 재양자화 → 캐시 재저장, 요청 `completed` |

참고(별도 시험): 캐시 사용 시 로딩 약 4.7~6.1초 / 최대 메모리 약 2.4GB, 캐시 없을 때 약 15.7~17.2초 / 약 14.6GB. 캐시로 로딩한 모델과 새로 양자화한 모델이 같은 시드로 만든 이미지는 픽셀 단위로 동일(최대 차이 0).

### 3.4 입력 검증·오류 처리

#### 요청 거절(HTTP 상태)
| 요청 | 결과 |
|---|---|

#### 비정상 값 (512×512, int8, 2스텝, 요청별로 하나씩 전송)
| 입력 | 결과 | 서버 |
|---|---|---|
| 빈 프롬프트 `""` | `completed`, 512×512 이미지 생성됨 | 정상 |
| 500×500 | `completed`, **실제 이미지 480×480** (로그: "height and width have to be divisible by 32 ... Dimensions will be resized accordingly") | 정상 |

| 시드 `2**70` | **HTTP 500** (`OverflowError: Python int too large to convert to SQLite INTEGER`) | 정상 |
| 크기 -64×-64 | `failed` (`Trying to create tensor with negative dimension -4`) | 정상 |

| 대상 | 결과 |
|---|---|
| `processing`으로 남은 작업의 `/result` | **HTTP 500** (`TypeError: can only concatenate str (not "NoneType") to str`) |
| `failed` 작업의 `/result` | **HTTP 500** (같은 오류) |

#### UI
- 없는 task_id를 조회하면 빨간 오류는 뜨지만, 직전에 보던 `completed` 상태·진행률·이미지가 그대로 남습니다.

### 3.5 성능과 메모리 (768×768, 20스텝, 시드 1, 서버 재시작 후)

| | 총 생성 시간 | 스텝당 | 비고 |
|---|---|---|---|
| int8 | 157.2초 | 약 7.9초 | 인코더 약 29초 + 캐시 로딩 후 생성 |
| bf16 | 519.2초 | 약 25.3초 | 인코더 생략(프롬프트 캐시), tqdm 20/20 8분 26초 |

- 비율: 총 시간 기준 bf16 / int8 = 약 3.3배.
- 512×512(20스텝)에서는 int8 약 65초(일정), bf16 73~134초.
- 스왑 사용량: 측정 구간에서 8.7~12.3GB 범위로 유지, 시간이 지나며 계속 증가하는 현상은 없었습니다.
- bf16 서버 프로세스는 768 생성 중 약 17GB를 사용한 적이 있고(이전 측정), 이는 이 머신에서 GPU가 쓸 수 있는 메모리 한도를 넘는 값입니다.

### 3.6 결과물 품질 (bf16 vs int8)

조건: 512×512, 20스텝, 시드 7, 같은 프롬프트. PSNR이 높을수록, MAE가 낮을수록 두 이미지가 비슷합니다.

| 프롬프트 | PSNR (dB) | MAE (/255) | 육안 비교 |
|---|---|---|---|
| 글자: `"OPEN 24 HOURS"` 네온 간판, 비 오는 밤 | 34.2 | 1.99 | 글자 철자·형태 모두 정확, 구분 어려움 |
| 인물: 노인 어부 클로즈업, 창가 자연광 | 28.4 | 3.38 | 구도·표정 동일, 눈·주름 세부만 미세하게 다름 |
| 유리잔: 물, 굴절·카우스틱 | 35.3 | 2.71 | 굴절·그림자 거의 동일 |
| 한국어: 눈 내리는 서울 거리, 한복·우산 | 30.7 | 4.29 | 한국어 프롬프트 정상 반영, 구도 동일 |
| (참고) 768×768 여우, 20스텝, 시드 1 | 30.4 | 3.87 | 구도·질감 거의 동일 |

- **결정성**: bf16을 같은 시드로 두 번 생성(요청 묶음 리팩터링 전/후)한 결과의 MAE가 0.00, 최대 차이 0이었습니다. 묶음 처리 도입이 출력을 바꾸지 않았습니다.
- 한 프롬프트당 한 장씩 비교한 결과라 통계적인 품질 평가는 아닙니다.

## 6. 수정 내역과 재검증

위 4번의 문제를 모두 고쳤습니다. 각 수정은 별도 커밋이며 아래 방법으로 다시 검증했습니다.

| # | 문제 | 수정 | 커밋 | 재검증 |
|---|---|---|---|---|
| 1 | 완료되지 않은 작업의 결과 조회가 500 | `queued`/`processing`은 409(`작업이 아직 완료되지 않았습니다.`), `failed`는 409(`작업이 실패해서 결과가 없습니다.`), 파일이 없으면 404 | `ff25b0f` | `TestClient` + 임시 DB로 6개 상태 케이스(queued, processing, failed, completed, 파일 없음, 없는 ID) 모두 기대한 코드 |
| 2 | 큰 시드가 500 | 시드를 `0 ≤ seed ≤ 2^63-1`로 제한(422) | `ff25b0f` | `2^70`, `2^63`, `-1`은 422, `2^63-1`은 200 |
| 3 | 크기·스텝·프롬프트 검증 없음 | 크기 64~1024이고 32의 배수, 스텝 1~100, 프롬프트 공백 제거 후 1~2000자. 범위 밖은 조용히 바꾸지 않고 422로 거절 | `ff25b0f` | 21개 입력 케이스(경계값 포함) 모두 기대한 코드. 프롬프트 앞뒤 공백 제거 확인 |
| 4 | UI에서 조회 실패 시 이전 상태가 남음 | 조회·생성 시작 때 상태·진행률·이미지 초기화, 서버 오류 메시지(`detail`) 표시, 입력칸에 서버와 같은 `min`/`max`/`step`/`maxLength` 적용 | `7205d0b` | 브라우저: 완료 작업 이미지를 본 뒤 없는 ID를 조회하면 상태·이미지가 지워지고 `작업을 찾을 수 없습니다.` 표시. 실패한 작업은 `failed`와 오류 표시. 범위 밖 값(Height 500)은 브라우저 단계에서 막혀 서버 요청 0건. `tsc`·`eslint` 통과 |

### 수정 중 추가로 발견해 함께 고친 것
- **종료 지연**: 기존 `stop()`은 큐에 쌓인 요청을 전부 처리한 뒤에야 종료했습니다. 대기열이 길면 서버 종료가 수 분 걸리는 문제였고, 5번 수정에 포함해 고쳤습니다.

### 수정 후에도 남는 사항
- 크기 상한(1024)과 프롬프트 상한(2000자)은 시험해본 범위를 보수적으로 잡은 값입니다. 1024 초과 해상도와 2000자 근처 프롬프트의 실제 동작은 시험하지 않았습니다. 값을 바꾸려면 `backend/app/schemas/generate/generate.py`와 `frontend/src/App.tsx`의 상수를 함께 수정해야 합니다.
- 없는 task_id 조회는 여전히 HTTP 400을 돌려줍니다(기존 동작 유지, 메시지는 UI에 표시됨).
- 서버를 강제 종료(`kill -9`, 전원 차단 등)하면 생성 중이던 작업은 `failed`로 처리되고(다음 시작 때) 다시 실행되지는 않습니다. 정상 종료(SIGTERM/Ctrl-C)일 때만 이어서 처리됩니다.
